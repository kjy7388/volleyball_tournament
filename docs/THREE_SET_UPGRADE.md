# 3세트·3판 2선승 및 승점 전환 — 로컬 개발 보고

작성일: 2026-11-02 (Asia/Seoul). 이번 작업에서는 로컬 코드·SQL·테스트만 변경했습니다. 실제 Supabase SQL 실행, 운영 경기·선수 수정, Git Commit/Push, Vercel 배포는 하지 않았습니다. MAD FC에는 접근하지 않았습니다.

현재 배포 사전 점검: 사용자가 SQL Editor에서 004를 적용했다고 알렸고, 실제 Data API에서 형식 4·배구 점수 4·통합 2를 확인했습니다. 에이전트는 원격 SQL을 실행하지 않았습니다. 아래 ‘미적용’ 상태와 테스트 수치는 초기 로컬 개발 당시의 기록이며, 적용 절차는 미적용 환경을 위한 안내입니다. 이미 적용된 SQL은 재실행하지 않습니다.

## 새 경기 모델

| 구분 | 배구 | 피구 |
| --- | --- | --- |
| 최대 / 승리 조건 | 3세트 / 2세트 선승 | 3판 / 2판 선승 |
| 기본 | 모든 세트 15점 | 판당 10분, 잔여 인원 0~10명 |
| 조별리그 | 듀스 없음. 15:14 종료, 16:14 거부 | 잔여 인원이 많은 반 승리 |
| 준결승·결승 | 2점 차 듀스. 15:14·16:15 미완료, 16:14·17:15 종료 | 조별리그와 같은 판 규칙 |
| 동률 | 최종 세트 무승부 불가 | 승부 미결정. 연장전/재경기 후 수동 승자 지정 기록 필수 |

배구는 `stage`를 기준으로 자동 분기합니다. 기존 목표 점수 설정 UI는 3개 세트로 유지하며 기본값을 모두 15점으로 변경했습니다. 결선 점수에 9999 같은 경기 규칙상 상한을 두지 않습니다. 프런트엔드 입력과 RPC JSON 숫자는 JavaScript 안전 정수 범위에서 다루며, DB 점수 열은 `numeric`입니다. 이 표현 범위는 듀스 승패 기준의 상한이 아닙니다. 10001:9999 듀스 결과도 테스트했습니다.

미완료 세트/판은 임시 저장만 가능하고 순위에는 반영하지 않습니다. 앞선 세트/판이 끝나지 않았거나 2승 이후 기록이 존재하면 저장을 차단합니다. 앞 판 수정 후 뒤 판은 자동 삭제하지 않고 모순을 표시하며, 관리자가 명시적으로 고치거나 비울 수 있습니다. 확정 취소는 기존의 ‘임시 저장으로 변경’ 확인 절차를 재사용합니다.

피구 판 JSON은 다음 네 필드로 구분합니다. 배구 점수와 혼용하지 않습니다.

```json
{"homeRemaining":5,"awayRemaining":5,"winner":"away","manualWinner":true}
```

미진행 판은 양쪽 잔여 인원·승자가 `null`, `manualWinner=false`입니다. 일부 인원만 입력했거나 동률 미해결인 현재 판은 임시 상태입니다. 일반 판은 입력값에 따라 승자를 자동 계산하고, 동률 수동 지정은 `manualWinner=true`로 저장하며 공개 상세에도 표시합니다. 동률이 아닌 경우 임의 승자 지정은 JS·RPC 양쪽에서 거부합니다.

## 승점과 순위

두 종목 모두 확정된 조별리그 경기만 2:0 승리 3점, 2:1 승리 2점, 1:2 패배 1점, 0:2 패배 0점을 부여합니다. 결선·임시 저장은 제외합니다.

- 배구: 승점 → 경기 승수 → 승리 세트/패배 세트 → 득점/실점 → 두 팀 간 직접 맞대결.
- 피구: 승점 → 경기 승수 → 승리 판/패배 판 → 잔여 인원 합계 차 → 두 팀 간 직접 맞대결.
- JS는 BigInt 교차곱, SQL은 numeric 교차곱으로 비교합니다. 배구 득점 합계도 JS 내부에서 BigInt로 정확히 합산한 뒤 문자열로 표시합니다. 저장 스냅샷에 BigInt·Infinity·NaN을 추가하지 않습니다.
- 분모 0·분자 양수는 `무패`로 표시하고 모든 유한 비율보다 우선합니다. 0/0은 `—`인 미기록이며 최상위로 취급하지 않습니다. 비율 표시만 소수 셋째 자리까지 반올림하고 순위 비교는 반올림하지 않습니다.
- 앞선 지표가 같은 두 팀만 직접 맞대결로 구분합니다. 세 팀 동률은 맞대결 승수로 임의 확정하지 않습니다. 해결되지 않은 동률 집단 안에서만 기존 관리자 수동 순위를 허용하고, 공개 화면에는 ‘관리자 확정’을 표시합니다.
- 양 조의 6개 경기와 순위가 모두 확정돼야 교차 준결승을 배정합니다. 기존 결선 보호·영향 확인·Revision 충돌·원자적 저장 구조를 유지합니다.

## 선수·화면

반별 정원은 10명이며 새 초기 샘플만 10명씩 생성합니다. 기존 실제·예시 선수는 추가·삭제·교체하지 않습니다. 10명 미만으로 저장할 수 있으며 관리자 카드에 부족 인원을 표시합니다. 10명이면 추가 버튼을 막고 JS·RPC·DB의 지연 제약 트리거도 초과 등록을 막습니다. 대시보드는 6개 반 중 정원 충족 수를 표시합니다.

순위표에 승점·비율·배구 득실점 또는 피구 잔여 인원 차를 추가했습니다. 모바일은 순위·반·승점·비율·진출을 우선 표시하고, 각 반의 ‘상세 기록’을 열면 경기 수·승패·모든 산정 지표를 확인할 수 있습니다. 기존 종목 탭, 메뉴, 브래킷, 일정, 상세 모달과 모바일 중앙 정렬은 유지합니다. 홈·경기 입력·조별리그·설정에 새 규칙을 안내합니다.

## 서버 변경과 보존 방식

신규 파일: `supabase/migrations/004_three_set_points_and_survivors.sql`.

기존 001·002·003은 수정하거나 원격에서 재실행하지 않습니다. 004는 기존 테이블·Auth·관리자 목록·RLS·감사 이력을 보존하고, 알려진 제약만 검토해 교체합니다. 예상하지 않은 점수 제약은 오류로 중단합니다. 새로운 피구 잔여 인원 열과 private 백업 테이블을 추가합니다.

버전 구분:

- 새 경기 형식 확인: `get_competition_format_version()` = **4**.
- 배구 점수 확인: `get_volleyball_scoring_version()` = **4**.
- 종목 구분 API: `get_sports_schema_version()` = **2** 유지.
- 대회 JSON/DB `schemaVersion` = **2** (기존 1에서 변경).

새 앱은 양 종목 모두 형식 버전 4 확인 전 조회·저장을 차단하고 004 안내를 보여줍니다. 따라서 실제 DB가 아직 기존 형식인 동안 localhost 일반 개발 서버에도 안내가 나오는 것이 정상입니다. 기능·화면 검증은 실제 Supabase에 연결하지 않는 Playwright/PGlite 환경에서 완료합니다. 기존 브라우저 인증 방식은 바꾸지 않습니다.

### 004가 중단하는 경우

- 기존 형식의 임시·확정 경기, 승자·확정 시각·경기별 규칙 기록이 존재함.
- 기존 어느 세트든 점수가 있거나 피구 어느 판이든 승자가 있음. 앞 3개만 호환돼 보여도 기존 결과를 추측해서 변환하지 않음.
- 반별 선수가 10명 초과함.
- 기존 스냅샷 구조 또는 점수 관련 제약 정의가 예상과 다름.

위 경우에는 전체 트랜잭션이 롤백됩니다. 특히 피구의 과거 ‘승자만 있는 기록’에는 잔여 인원을 만들어 넣지 않습니다. 기존 결과나 선수 정리가 필요하면 DB·JSON 원본 백업을 확보하고 사용자에게 처리 범위를 확인해야 합니다. 004를 실행하기 위해 경기 결과를 임의로 지우거나 재저장하지 마세요.

### 호환되는 빈 경기 상태의 전환

1. 원본 대회 스냅샷을 비공개 `volleyball_private.rule_upgrade_backups`에 보관합니다. 기존 감사 이력은 수정하지 않습니다.
2. 기존 설정·반·선수·경기 ID·일시·장소를 유지합니다. 배구 기본 목표를 15·15·15로, 스냅샷 버전을 2로 바꾸고 Revision을 1 증가시킵니다.
3. 예전 4·5번째 **빈 placeholder 행은 DB에 그대로 남깁니다**. 신규 공개 조회는 1~3번을 반환하며, 트리거가 향후 4·5번 INSERT/UPDATE를 거부합니다. 추가 CHECK도 뒤쪽 행에 값이 들어가는 것을 막습니다. 경기 기록·빈 행 모두 DELETE하지 않습니다.
4. 새 RPC는 3개 세트/판만 검증·업서트합니다. 같은 대회 Revision 충돌, 결선 결과 변경 확인, 종목별 잠금과 트랜잭션 롤백을 유지합니다.

로컬 테스트에서 빈 기존 데이터의 선수 8명·일정·원본 백업·정책·기존 빈 45행이 보존되고 새 공개 결과만 3개로 반환되는지 확인했습니다. 11명 정원 초과, 과거 피구 결과, 알 수 없는 CHECK에서는 실제로 적용 전체가 롤백됐습니다.

## 실제 DB 적용 전 사용자 작업

1. 편집을 잠시 멈추고 기존 절차로 roles/schema/data 수동 DB 백업과 각 종목 JSON 원본을 확보합니다. 이번 소스 ZIP은 DB·Auth 백업이 아닙니다.
2. `supabase/checks/three_set_preflight.sql`을 SQL Editor에서 읽기 전용으로 실행해 실제 함수 정의·권한·제약·선수 수·기록을 확인합니다. 이 점검 파일 자체는 로컬 DB에서도 실행 검증합니다. 원격 SQL 실행은 이번 작업에 포함하지 않습니다.
3. 기록이나 정원 초과가 있으면 중단합니다. 원본을 보관하고 처리 방식에 대한 별도 승인을 받아야 합니다. 004는 이를 자동 해결하지 않습니다.
4. 사용자 승인 후 **004만** 적용합니다. 실패하면 오류를 검토하고 실패한 트랜잭션을 종료합니다. 001·002·003으로 되돌리려 하지 않습니다.
5. 기존 선수·경기 수와 백업, 새 버전 4/4/2, JSON 버전 2·각 3개 결과를 읽기 전용으로 확인합니다. 양 종목은 계속 6개 반·9경기입니다.
6. 별도 승인으로 새 프런트엔드를 Commit/Push·기존 Vercel에 배포합니다. 전환 전후 구 앱·새 앱 관리자의 동시 편집은 피합니다.
7. 실제 관리자 Auth, 새 규칙 저장, 공개 화면 갱신·Realtime은 승인된 테스트 범위에서 별도로 검증합니다. 이번 작업은 운영 쓰기를 하지 않습니다.

이번 읽기 전용 공개 조회에서는 배구 Revision 17, 피구 Revision 3이며 두 종목 모두 예정 9경기, 각 반 8명, 새 규칙 전환을 막는 공개 결과는 없었습니다. 이는 공개 스냅샷 범위의 관찰이며 private 이력·실제 함수 정의·전체 DB 백업 검토를 대신하지 않습니다. 적용 직전 다시 점검해야 합니다.

작업 종료 시점에도 양 종목 공개 스냅샷 해시와 Revision이 시작 시점과 같았습니다. Data API는 기존 배구 규칙 버전 3·통합 버전 2를 반환했고, 신규 형식 함수는 404/PGRST202였습니다. 004는 실제 프로젝트에 미적용 상태입니다.

수정 전 소스는 저장소 밖 `..\sports-v4-backup-20261102\source-before.zip`에 보관했습니다. 환경변수와 비밀번호를 백업·로그·보고서에 넣지 않았습니다. 공개 상태 비교 파일도 수량·Revision·해시 등 비식별 메타데이터만 저장합니다.

전체 검사는 각각 1회 실행하며, 개발 중 실패는 해당 파일/케이스만 먼저 재검증했습니다. 첫 기존 규칙 갱신 검사에서는 121개 통과·25개 실패가 나왔습니다. 대부분 숫자형 CHECK의 재실행 비교 오류가 만든 후속 트랜잭션 실패와 과거 fixture의 대회 상태 값이 원인이었습니다. 이 두 원인과 남은 2개 기대값을 수정해 실패한 범위를 재검증했고 최종 전체 단위 검사가 통과했습니다. 브라우저 관련 26개도 사전 통과했습니다.

최종 검토에서 설정 화면에도 공통 승점 안내를 표시하도록 보완했고 설정·일정·상세 결과 케이스 1개만 재검증해 통과했습니다. 구 JSON 버전 안내를 ‘초기화’ 대신 원본 보존·004 검토로 바꾼 뒤 해당 단위 케이스만 확인했습니다. 이후 최종 빌드도 통과했습니다. 전체 테스트를 반복 실행하지 않았습니다.

실제 Supabase 004 적용·신규 결과 저장, 실제 관리자 계정 로그인, 실제 Realtime 수신, 실제 기기의 Safari, 새 규칙의 Vercel 배포는 미검증입니다. 운영용 Smoke Test는 새 규칙 배포 후 실행하도록 기대값만 갱신했으며 이번에는 원격 사이트에 실행하지 않습니다.
