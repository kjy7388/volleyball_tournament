# 배구 전 경기 무듀스 전환 — 운영 기록 보존

## 변경 범위

배구 조별리그와 동일하게 준결승·결승에서도 목표 점수 선취로 종료한다. 기본 15점, 3세트 2선승은 유지한다. 15:14는 종료, 14:14는 임시 점수, 16:14·16:15는 거부한다. 저장된 목표 점수 스냅샷을 자동 변경하지 않는다. 승점·순위·대진 계산, 피구 규칙, 선수 명단, 관리자 인증, RLS, Realtime, 저장 RPC 인터페이스는 유지한다.

## 현재 확인과 한계

2026-11-24 작업 시작 시 공개 Data API를 GET으로 조회했다. 배구 Revision 28·선수 60명, 피구 Revision 16·선수 90명이었고, 조회 시점에는 두 종목 모두 9경기가 예정 상태였으며 입력된 배구 세트 점수는 없었다. 새 규칙과 충돌하는 점수는 발견되지 않았다. 이 조회는 그 시점의 공개 데이터 확인이며 백업이나 이후 데이터의 호환성을 보장하지 않는다.

서버 버전은 배구 4, 피구 6, 선수 등록 5, 경기 형식 4, 종목 통합 2였다. 실제 함수 정의, 관리자 멤버십, 비공개 감사 이력은 Data API로 조회하지 않았다. 아래 사전 점검 SQL로 프로젝트 소유자가 별도로 검토해야 한다. 원격 SQL은 실행하지 않았다.

## 실제 적용 순서 — 사용자 승인 전 실행 금지

1. 관리자 결과 입력을 잠시 중단하고 현재 경기·선수·일정·대진·Revision을 확인한다. 운영 중 새 기록이 생겼으면 점검을 다시 수행한다.
2. 프로젝트 폴더 밖에 복원 가능한 수동 DB 백업(roles.sql, schema.sql, data.sql)을 확보한다. 기존 배포 관리자 화면에서 두 종목 JSON도 별도로 보관한다. CSV 점검 결과나 해시는 복원 가능한 백업이 아니다. 백업은 Git에 넣지 않는다.
3. `supabase/checks/volleyball_no_deuce_all_stages_preflight.sql`을 검토 후 SQL Editor에서 실행하고 한 행·한 JSON 컬럼 전체를 저장한다. 경기 점수·상태·대진·선수 수·Revision·감사 이력 해시·관리자 멤버십 해시·RLS·함수 정의·실행 권한을 확인한다. 개인정보와 Auth ID는 직접 출력하지 않는다.
4. `deuce_scores`나 `obvious_score_conflicts`가 비어 있지 않거나 함수·권한이 예상과 다르면 중단한다. 16:14·17:15 등의 과거 기록을 15점으로 줄이거나 삭제·확정 취소·대진 재생성하지 않는다. 경기별 처리에는 별도 사용자 승인이 필요하다.
5. 사용자가 승인한 뒤 `supabase/migrations/007_volleyball_no_deuce_all_stages.sql` 전체 트랜잭션을 실행한다. 001~006은 다시 실행하지 않는다. 007은 테이블 변경이나 UPDATE/DELETE/TRUNCATE/INSERT 없이 점수 검증 함수와 배구 규칙 버전 함수만 교체한다.
6. 007은 예상 버전·함수 정의를 검사하고, 저장된 배구 점수와 승자·기존 순위·대진의 일관성을 검증한다. 충돌이 생기면 경기 ID·라운드·상태와 함께 오류를 내고 전체 롤백한다. 실패한 SQL Editor 세션이 트랜잭션 상태를 유지하면 `ROLLBACK;`으로 종료한다. 자동 복구나 재저장은 하지 않는다.
7. 같은 사전 점검 SELECT를 다시 실행한다. `tournaments`의 전체 스냅샷·선수 명단 해시, 경기 점수·확정 상태·승자·일정·조·대진·Revision, 감사 이력·관리자 멤버십 해시·RLS·Realtime이 전과 같아야 한다. 바뀌어야 하는 것은 4인자 `score_result`의 정의와 배구 규칙 버전 7뿐이다.
8. Data API에서 배구 버전 7, 피구 6, 선수 등록 5, 경기 형식 4, 종목 통합 2를 읽기 전용으로 확인한다. 사용자 승인 후 프런트엔드 Commit·Push·배포를 진행한다. 새 프런트엔드는 배구 서버 버전이 7이 아니면 안내를 표시하며 배구 조회·저장을 차단한다.
9. 새 배포의 규칙 안내·로그인 화면·공개 경기 결과를 먼저 읽기 전용으로 확인한다. 기존 관리자 탭은 새로고침한다. 운영 결과를 임의의 테스트 점수로 저장하지 않는다. 서버와 클라이언트가 일치한 뒤 관리자 입력을 재개한다.

## 로컬 검증

기존 001~006 적용은 새 일회성 PGlite 테스트 DB에서만 수행한다. 기존 완료 경기·선수 순서·조별 순위·준결승 대진·피구·Revision·감사 이력·RLS 및 RPC 정의를 비교한다. 호환되지 않는 과거 결선 점수가 있으면 007의 함수·버전 교체까지 전부 롤백되는지 검증한다. 사전 점검 SQL도 로컬에서만 실행한다.

- 전체 단위·DB 테스트 16개 파일, 285개 모두 통과. 전체 실행은 한 번만 수행했다.

- 작업 종료 시 공개 Data API를 GET으로 다시 확인했다. 배구 Revision 28·선수 60명, 피구 Revision 16·선수 90명이 그대로였고, 두 종목 전체 공개 스냅샷의 SHA-256이 작업 시작 시점과 일치했다. 충돌 점수도 없었다.
- 실제 서버 함수 정의·관리자 멤버십·감사 이력의 사전 점검 SQL 실행 및 007 적용은 미실행이다. 운영 Realtime 수신이나 운영 쓰기 테스트도 수행하지 않았다.
- 실제 Supabase SQL 실행, 운영 데이터 저장·삭제, Git Commit·Push, Vercel 배포는 하지 않았다.
