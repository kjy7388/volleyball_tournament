# 상단 문구·배구 듀스 제거 — 로컬 변경 및 적용 안내

작성일: 2026-11-01. 기존 001·002 SQL과 관리자 인증·RLS·피구 규칙·모달 스크롤 잠금 구현은 변경하지 않았습니다. 기존 QA 작업 파일도 보존했습니다.

현재 상태: 사용자가 Supabase SQL Editor에서 003을 적용했다고 알렸고, 배포 사전 점검에서 실제 Data API의 `get_volleyball_scoring_version()` = 3, `get_sports_schema_version()` = 2를 확인했습니다. 에이전트는 원격 SQL을 실행하거나 운영 데이터를 변경하지 않았습니다. 이미 적용된 001·002·003은 재실행하지 않습니다. 아래 적용 순서는 미적용 환경을 위한 절차이며, 초기 개발 당시의 검사 결과와 현재 적용 상태를 구분합니다.

모바일 헤더는 600px 이하에서 로고를 상단 중앙에 독립 배치하고 소개 문구를 같은 전체 너비 중심축에 세로 정렬합니다. 320·375·390·430px 및 태블릿 768px·PC 1440px을 검사하는 `tests/mobile-header-center.spec.js` 6개를 추가했습니다. 기존 인증·탭·메뉴·저장 구조는 유지합니다.

## 화면 변경

`src/components/TournamentIntro.jsx` 하나를 공통 Header에서 사용합니다. 배구·피구의 공개 화면과 관리자 화면에 같은 소개를 표시합니다.

- 영문 라벨: `SPORTS TOURNAMENT`
- 메인 제목: `화곡중학교 배구·피구 대진표`
- 부제목: `3학년 전환기 프로그램`
- 파란색 슬로건: `CLASS TOGETHER. PLAY TOGETHER.`

제목의 구분 문자는 U+00B7이며 브라우저 테스트에서 문자열 전체와 코드 포인트를 검사합니다. 브라우저 탭 제목도 통일했습니다. 홈의 기존 소개용 문구는 종목별 대회 현황 제목으로 정리하고 우승 강조·트로피·네이비 히어로·종목 탭·공개 메뉴·관리자 버튼 구성은 유지했습니다. 일반 화면의 관리자 이동 버튼은 추가하지 않았습니다.

320px 피구 순위표 검사에서 표의 최소 너비가 바깥 그리드까지 확장되는 현상도 발견했습니다. 조별리그 열에 `min-width: 0`만 지정해 기존 표 내부 스크롤 영역을 유지하고 페이지 전체가 늘어나지 않도록 보완했습니다. 열·색상·정보·표 디자인은 그대로입니다.

## 배구 검증 방식

`analyzeSets`가 최종 확정 오류(`errors`)와 임시 저장도 불가능한 오류(`draftErrors`), 세트 상태(`setStates`)를 구분합니다. 순위와 대진은 기존 계산 구조를 유지하면서 이 검증 결과를 재사용합니다.

| 입력 | 임시 저장 | 최종 세트 인정 |
| --- | --- | --- |
| 25:24, 24:25, 25:0, 0:25 | 가능 | 가능 |
| 24:24 | 가능 | 불가 |
| 26:24, 26:25, 25:25 | 불가 | 불가 |
| 5세트 15:14, 14:15, 15:0, 0:15 | 가능 | 가능 |
| 5세트 14:14 | 가능 | 불가 |
| 5세트 16:14, 16:15, 15:15 | 불가 | 불가 |

기본 목표는 25·25·25·25·15점이며 기존 설정의 목표 점수와 경기별 `rulesSnapshot`을 유지합니다. 한쪽만 해당 목표에 정확히 도달하고 상대는 목표 미만이어야 합니다. 미완료 세트 뒤의 다음 세트 입력, 세트 건너뛰기, 음수·소수·비숫자, 3승 뒤 추가 입력을 거부합니다. 미완료 세트에는 승수를 주지 않고 미확정 경기는 순위에 반영하지 않습니다.

관리자 입력창에 목표 점수·미진행/진행 중/종료 가능/입력 확인 상태를 표시합니다. 임시 저장과 최종 확정 버튼은 서로 다른 검증을 사용합니다. 이전 세트를 수정해 뒤 세트가 모순되면 입력을 보존하고 오류를 표시하며, 관리자가 수정하거나 비워야 저장할 수 있습니다. 입력을 자동 삭제하지 않습니다.

JSON 복원도 동일한 검증을 사용합니다. 과거 듀스 점수가 있는 백업을 자동 보정하거나 DB에 덮어쓰지 않습니다. 호환되지 않는 백업은 오류를 안내하고 원본 파일은 보존합니다. 기존의 빈 DB 전용 최초 복원·Revision 충돌·결선 영향 확인 기능은 유지합니다.

피구의 판별 승자 모델·5판 3선승·동률·관리자 순위 확정 규칙은 변경하지 않았습니다. 배구와 피구의 저장·Revision·선수·결과는 계속 분리됩니다.

## 서버 변경과 로컬 검증

새 마이그레이션은 `supabase/migrations/003_volleyball_no_deuce.sql`입니다. 기존 `save_tournament` → `validate_snapshot` → `volleyball_private.score_result` 경로에서 마지막 점수 검증 함수만 교체합니다. 공개 저장 RPC, 원자적 트랜잭션, Revision 검사, 결선 기록 확인, 관리자 검사와 RLS 정책을 재작성하지 않습니다.

003은 레코드를 수정·삭제하지 않습니다. 트랜잭션 안에서 기존 배구 스냅샷 전체를 새 규칙으로 검증하며, 과거 초과 점수나 모순된 임시 기록이 있으면 `NO_DEUCE_EXISTING_RESULT_REVIEW_REQUIRED` 오류로 전체 적용을 중단합니다. 유효한 기존 기록·Revision·설정·피구 결과·관리자·정책이 유지되는지 로컬 PGlite에서 확인했습니다. 비호환 기록이 있을 때 함수 교체까지 롤백되는지도 검사했습니다.

`get_volleyball_scoring_version()` 공개 읽기 함수는 3을 반환합니다. 통합 데이터 모델 버전은 계속 2입니다. 새 프런트엔드는 배구 저장 전에 점수 버전 3을 확인하고, 003 미적용 시 설명을 표시하며 저장 RPC를 호출하지 않습니다. 피구 저장에는 이 검사를 적용하지 않습니다. private 점수 함수는 클라이언트가 실행할 수 없습니다.

`supabase/checks/volleyball_no_deuce_preflight.sql`은 실제 함수 정의, SECURITY DEFINER 여부, 실행 권한, 배구 Revision·목표 점수, 명백한 점수 충돌을 한 JSON 셀로 조회하는 SELECT입니다. 선수 명단·Auth 정보·관리자 행을 조회하지 않습니다. 이 점검 SQL 자체도 로컬 DB에서 실행했습니다. 단순 점수 목록은 전체 순서 검증을 대신하지 않으며, 003의 스냅샷 검증이 최종 안전장치입니다.

초기 개발 시 실제 프로젝트는 공개 조회만 수행했습니다. 당시 배구 6개 반·9경기, 피구 6개 반·9경기를 확인했으며 새 점수 버전 함수는 아직 없었습니다. 이후 사용자가 003을 적용했고 최신 Data API 점검에서는 버전 3을 확인했습니다. 초기 공개 스냅샷 기준 배구의 새 규칙 비호환 경기는 0개였습니다. 익명 클라이언트로는 private 함수 정의를 확인할 수 없습니다. 공개 조회는 전체 DB·Auth·감사 데이터의 백업이 아닙니다.

점검 전후 공개 스냅샷 해시가 양 종목 모두 같았습니다. 배구 Revision 17, 피구 Revision 2와 각 6개 반·9경기가 그대로 유지됐습니다. 이 확인은 공개 스냅샷 범위이며 비공개 테이블 전체의 동등성을 의미하지 않습니다.

수정 전 소스 백업은 프로젝트 밖 `..\volleyball-no-deuce-backup-20261101\source-before.zip`에 저장했습니다. 환경변수·Git·빌드·의존성·테스트 산출물은 제외했습니다. 공개 데이터 점검 결과는 같은 외부 폴더에 수량·Revision·해시 등 비식별 메타데이터만 기록했습니다.

## 실제 적용 순서 — 사용자 확인 후 진행

1. 대회 편집을 잠시 멈추고 기존 절차로 DB의 roles/schema/data 백업을 확보합니다. JSON 대회 백업도 별도로 보관합니다. 현재 작업의 소스 ZIP과 공개 메타데이터는 이 DB 백업을 대신하지 않습니다.
2. 기존 프로젝트 SQL Editor에서 읽기 전용 `volleyball_no_deuce_preflight.sql`을 검토·실행합니다. 함수 정의와 권한이 소스 001·002의 예상 구조와 일치하는지 확인하고, 과거 듀스 결과·모순된 임시 점수가 있으면 먼저 보고합니다. 원본을 지우거나 임의로 점수를 줄이지 않습니다.
3. 사용자 승인 후 **003만** 실행합니다. 001·002를 다시 실행하지 않습니다. 오류가 발생하면 중단하고, 원인을 검토할 때까지 기존 데이터를 수정하지 않습니다. SQL Editor 세션이 실패한 트랜잭션에 남으면 `ROLLBACK`으로 종료하며 003을 무리하게 재시도하지 않습니다.
4. 읽기 전용 `select public.get_volleyball_scoring_version();` 결과 3, 통합 버전 2, 기존 수량·Revision·양 종목 결과·관리자 권한이 유지되는지 확인합니다. Data API 스키마 갱신이 반영됐는지도 확인합니다.
5. 새 프런트엔드를 localhost에서 확인한 뒤 별도 승인으로 Commit/Push·기존 Vercel 자동 배포를 진행합니다. 서버 변경과 프런트엔드 변경 사이에는 관리자 입력을 재개하지 않습니다. 기존 프런트엔드는 여전히 2점 차 규칙을 사용하므로 동시 편집을 피합니다.
6. 승인된 테스트 환경에서 실제 관리자 Auth·25:24/15:14 저장·초과 점수 거부·결과 수정·로그아웃·익명 브라우저 갱신을 확인합니다. 현재 작업에서는 실제 경기 결과를 입력하지 않았으므로 이 단계와 실제 Realtime 이벤트 수신은 미검증입니다.

003은 안전하게 기존 기록을 보존하는 대신 비호환 기록이 있으면 적용하지 않습니다. 과거 기록을 어떻게 처리할지는 백업 확인과 사용자 결정이 필요합니다. 프런트엔드만 먼저 배포하지 마세요.
