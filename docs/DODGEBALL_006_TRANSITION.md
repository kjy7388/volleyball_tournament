# 피구 합산 잔여 인원 규칙 전환 (006)

이번 변경은 로컬 개발용이다. 원격 SQL 실행, Commit/Push, 배포, 운영 기록 수정은 하지 않았다.

## 규칙과 저장 모델

- 배구의 규칙·승점은 그대로 유지한다. 피구만 기본 2세트 잔여 인원 합계로 경기 승자를 정한다.
- 1·2세트 합계가 다른 경우 3세트 입력을 거부하고 승점 3/0을 적용한다.
- 합계 동점이면 3세트를 진행하고 경기 승점 2/1을 적용한다. 3세트도 동점이면 관리자가 별도 절차 후 경기 승자를 지정한다.
- 각 세트의 숫자 비교로 세트 승패를 집계한다. 동률 세트는 승리·패배에 포함하지 않는다. 3세트 수동 지정은 경기 승패만 바꾼다.
- `match_rounds`와 기존 `rounds` JSON 구조를 재사용한다. `winner`는 일반적으로 세트 승자이며, 3세트 동률의 `manualWinner: true`일 때만 최종 경기 승자를 의미한다. 이 경우 세트는 여전히 무승부다.
- 실제 진행한 모든 세트의 인원 차이를 합산한다. 임시 결과와 결선은 조별 순위에서 제외한다.
- 인원은 음수가 아닌 정수다. 10명/5명 상한은 없으며 JS와 JSON의 정밀도를 위한 안전 정수 범위만 검증한다. 합계·차이·비율 비교에는 BigInt/PostgreSQL numeric을 사용한다.
- 경기 시간(10분, 운영 상황에 따라 6분·7분)은 안내만 제공한다. 시간이나 출전 선수 선택을 새로 저장하지 않는다.
- 공개 경기 카드의 피구 스코어는 세트 승수 대신 합산 잔여 인원을 표시한다. 3세트 동률의 수동 경기 승자는 별도로 표시한다. 상세 기록 모달의 카드 디자인은 유지한다.

## 실제 DB 적용 전 필수 절차

1. 현재 배포 버전에서 배구·피구 JSON 백업을 각각 내려받고, 프로젝트 폴더 밖에 roles/schema/data 수동 DB 백업을 확보한다. 비밀번호·키·선수 명단이 들어간 백업은 Git에 넣지 않는다.
2. SQL Editor에서 기존 버전 5/4/4/2를 확인한다. 001~005를 다시 실행하거나 수정하지 않는다.
3. `supabase/migrations/006_dodgeball_aggregate_survivors.sql` 전체를 검토하고 사용자 승인 후 실행한다. 앞부분만 나눠 실행하지 않는다.
4. 006은 트랜잭션 안에서 기존 함수 정의를 점검하고, 새 판정·순위·결선 기준으로 기존 피구 스냅샷을 검증한다. 공개 대회·선수·경기 행과 Revision은 변경하지 않는다. 호환되는 경우 비공개 복구 스냅샷을 추가한다.
5. `006_INCOMPATIBLE_DODGEBALL_DATA` 오류는 기존 기록·수동 순위·결선 대진이 새 규칙에 맞지 않는다는 뜻이다. 전체 트랜잭션을 롤백하고 적용을 중단한다. 예: 1·2세트 합계가 다른데 기록된 3세트, 1·2세트 동률의 수동 세트 승자, 합산 기준과 다른 경기 승자, 새 순위와 다른 이미 진행된 결선.
6. 오류가 나면 기존 서비스와 백업을 보존하고 관리자와 경기별 처리안을 검토한다. 자동 초기화, 세트 잘라내기, 인원 추정, 과거 승자 변경을 하지 않는다. 별도 승인 없이는 재입력·정리도 진행하지 않는다. SQL Editor가 실패 트랜잭션 상태를 유지하면 `ROLLBACK;`으로 종료한다.
7. 적용 성공 후 다음 읽기 전용 조회를 확인한다. 새 클라이언트는 피구 버전 6이 없으면 피구 조회·저장을 막고 마이그레이션 안내를 표시한다. 배구에는 이 확인을 요구하지 않는다.

```sql
select public.get_dodgeball_scoring_version() as dodgeball_version,
       public.get_roster_registration_version() as roster_version,
       public.get_competition_format_version() as format_version,
       public.get_volleyball_scoring_version() as volleyball_version,
       public.get_sports_schema_version() as schema_version;
-- expected: 6, 5, 4, 4, 2
```

8. Data API에서도 새 함수가 익명 호출 가능한지 확인한다. 승인 후 프런트엔드를 배포하고 양 종목 조회·피구 입력·세트 무승부·동률 수동 승자를 검증한다. 기존 클라이언트와 새 서버의 규칙이 다르므로 적용·배포 시간에 관리자 결과 입력을 잠시 중단한다. 구버전 관리자 브라우저는 새로고침한다.

## 검증 범위

로컬 PGlite에서 001~005로 만든 일회성 테스트 DB에만 006을 적용한다. JS/SQL 판정 일치, 혼합 결과 순위, 9경기 결선, 원자적 저장·롤백, RLS, Revision 충돌, 재실행 보존, 비호환 기존 데이터의 전체 롤백을 검증한다. 브라우저 테스트는 모의 Supabase와 이 테스트 DB만 사용한다.

실제 Supabase 데이터 호환성, Data API 버전 6, 원격 RLS와 Realtime 이벤트 수신은 이번 작업에서 검증하지 않았다. 로컬 성공을 실제 운영 DB 적용 성공으로 간주하면 안 된다.
