# 배구·피구 통합 개발 검증 결과

검증일: 2026-11-01. 기존 프로젝트에서 코드·SQL 작성 및 로컬 검증을 수행했습니다. 원격 Supabase에 002를 실행하지 않았고, 원격 데이터 수정·계정 생성·Git Commit/Push·Vercel 배포는 하지 않았습니다.

위 설명과 아래 원격 미검증 목록은 초기 통합 개발 당시의 기록입니다. 이후 사용자가 002 적용과 실제 관리자 기능의 localhost 확인을 완료했다고 보고했습니다. 이번 배포 전 점검에서는 SQL 재실행 없이 공개 조회 RPC로 DB 버전 2, 배구 Revision 17·피구 Revision 2, 각각 6개 반·9경기를 직접 확인했습니다. 실제 비밀번호 로그인·운영 데이터 쓰기는 자동 검증하지 않으며 실제 Realtime·다중 세션 부하는 여전히 별도 확인 대상입니다.

## 실행한 자동 검증

Node 22 환경에서 실행했습니다.

브라우저 구성: 기존 대회·인증 23개, 모달 스크롤 11개, 공개 내비게이션 8개, 통합 종목 8개, 총 50개입니다.

- 일반 10개 화면과 관리자 8개 화면, 기존 URL 9개 리다이렉트, 탭 전환 및 관리자 로그인 유지.
- 피구 9경기 실제 입력→DB 확정→순위→준결승→결승→우승, 별도 브라우저 문맥 조회 및 새로고침.
- 피구 임시 저장·결과 수정·확정 취소·재확정, 실패 시 입력 유지·재시도, 판 수정 후 이후 입력 제거, 3승 후 비활성.
- 선수·설정·경기 결과·데모·초기화의 종목별 독립, 명단 최초 복사 확인과 기존 데이터 덮어쓰기 방지.
- 순환 동률 수동 확정과 ‘관리자 확정’ 표시, 이미 진행한 결선 수정 영향 경고와 취소 보존.
- 늦은 배구 조회 응답이 피구에 섞이지 않는지, Realtime을 차단한 상태의 포커스 재조회.
- 320·390·768·1440px 양 종목 화면 가로 넘침 검사, 기존 375·1024px 검증도 유지.
- 웹폰트가 없어도 320px 로고 정렬 및 종목 탭 가독성 유지.
- 중첩 모달·저장 성공/실패·ESC/외부 클릭·페이지 이동·선수 관리/설정/상세보기의 스크롤 복원. Chromium CDP 터치 스와이프도 검증.

브라우저 테스트의 Auth·HTTP는 모의 전송이며 SQL/RPC는 실제 PGlite 엔진에서 실행합니다. 가짜 프로젝트 URL과 5174 테스트 서버를 사용하고 Realtime WebSocket은 차단합니다. 운영 Supabase로 저장하지 않습니다. 기존 AuthProvider·AdminGuard·모달 잠금 코드는 수정하지 않았습니다.

## 실제 프로젝트를 읽기 전용으로 확인한 항목

- 기존 `.env.local`의 URL·Publishable Key로 공개 배구 스냅샷 조회 성공.
- 소스 ZIP·환경파일·공개 배구 JSON을 저장소 바깥에 백업. 이것은 소유자 권한의 전체 DB/Auth/정책 백업이 아닙니다.
- 해당 JSON을 격리 로컬 DB에 가져와 001→002 업그레이드 후 **Revision 17, 6개 반, 9경기, 선수 및 경기 결과 동일** 확인.
- localhost 5173 실제 공개 배구 화면 조회, 관리자 링크 0개, 피구의 002 적용 필요 안내, 직접 관리자 URL 로그인 화면 확인. 이 브라우저 확인에서는 공개 조회 RPC 외 Supabase 요청을 차단했습니다.
- 마지막 원격 공개 스냅샷이 시작할 때의 백업과 완전히 동일함을 확인(Revision 17). 원격 쓰기는 수행하지 않았습니다.
- `.env.local` 해시 및 MAD FC의 작업 시작/종료 Git 상태·HEAD가 동일합니다. 실제 키는 출력하거나 소스에 넣지 않았고 `.env.example`은 이름과 빈 값 두 줄만 유지합니다.

## 실제 환경에서 미검증 / 승인 후 확인 필요

- 실제 Supabase 002 적용, 실제 서버의 전체 스키마·함수·RLS/grants 차이. 공개 스냅샷만으로 소유자 수준의 상태를 확인했다고 주장하지 않습니다. `multi_sport_preflight.sql`을 소유자가 검토 후 실행해야 합니다.
- 기존 실제 관리자 계정의 이메일/비밀번호 로그인과 실제 JWT에 대한 RLS 쓰기 검증. 로컬 Auth UI 흐름 및 SQL 권한은 모의 인증/로컬 역할로 검증했습니다.
- 실제 Supabase Realtime 이벤트 수신·재연결 및 실제 서로 다른 기기/네트워크의 결과 동기화. 구독 필터/해제는 단위 테스트, 대체 재조회는 브라우저 테스트로 검증했습니다.
- 독립적인 여러 PostgreSQL 세션의 실제 잠금 경합·네트워크 지연 하중. 로컬 PGlite는 단일 연결이므로 함께 제출한 요청도 직렬 처리됩니다. 대회별 advisory lock과 행 잠금, Revision 충돌/중복 요청 거부는 구현·로컬 검증했지만 실제 병렬 트랜잭션 부하 검증을 대체하지 않습니다.
- 전체 DB/Auth 백업의 실제 복구, 운영 테스트 데이터 정리. 어떤 데이터도 정리하지 않았습니다.
- 실제 iOS Safari 하드웨어 및 Vercel 배포 후 직접 URL/새로고침/환경변수 확인. 모바일 검증은 데스크톱 Chrome의 뷰포트·터치 모사입니다.

## 재실행 및 이전 절차

`npm test`, `npm run build`, `npm run test:e2e`를 실행합니다. 테스트 중 소스를 수정하지 않습니다. 시스템 Node 24.13.0의 Windows 종료 문제가 있으면 `.nvmrc`의 Node 22로 실행합니다.

[통합 전환 절차](MULTI_SPORT_UPGRADE.md)에 백업·읽기 전용 사전 점검·002 적용·명단 최초 생성·실제 검증·기존 Vercel 프로젝트 배포 순서를 정리했습니다. 기존 DB에는 001을 다시 적용하지 않습니다. 사용자 승인 전에는 원격 SQL 실행·데이터 정리·Push·배포를 진행하지 않습니다.
