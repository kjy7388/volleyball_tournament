## 1. 최종 결과와 변경 범위

**빌드 성공, 기존 단위·DB 111개, 기존 브라우저 50개, 추가 로컬 시뮬레이션 6개, 추가 운영 Smoke Test 15개가 최종 통과했습니다.** 서로 다른 사례는 총 182개입니다. `npm test`와 `npm run test`는 같은 111개를 실행하므로 반복 실행을 별도 사례로 합산하지 않았습니다.

실제 운영 홈페이지에서 재현된 출시 차단 기능 오류는 발견되지 않았습니다. 다만 **경기 날짜·시간, 대회 기간, 실제 선수 명단 및 기존 종료 기록의 용도 확인은 대회 시작 전 필수 준비 항목**입니다. Realtime 이벤트 수신과 운영 관리자 쓰기 등 미검증 항목까지 성공한 것으로 판단하면 안 됩니다.

새로 작성한 테스트의 최초 실행 중 수집기·선택자 문제를 발견했습니다. 아래 5절에 최초 실패와 진단·수정·재실행 결과를 모두 기록했습니다. 앱 기능이나 운영 DB를 고쳐서 통과시킨 것이 아닙니다.

- 이번 변경: `playwright.production.config.js`, `tests-production/`, `playwright.simulation.config.js`, `tests-simulation/`, 실행용 npm scripts, 본 보고서.
- 앱 `src`, SQL 마이그레이션, 환경파일, 배포 설정은 수정하지 않았습니다.
- 실제 DB 마이그레이션 재실행, 운영 데이터 변경, Git Commit·Push, Vercel 재배포, 새 프로젝트 생성은 수행하지 않았습니다.
- 로컬 관리자/시뮬레이션의 쓰기와 SQL 실행은 가짜 Supabase 전송·메모리 PGlite에만 적용했습니다. 운영 계정으로 로그인하지 않았습니다.

### 운영 브라우저 감사 수치

- 직접 접속·새로고침 도우미 호출 **99건**. 탭·메뉴 클릭은 추가로 검사했습니다.
- 관찰한 공개 대회 조회 RPC 응답 **215건**. 허용된 종목 ID와 HTTP 200을 확인했습니다.
- 예상하지 못한 HTTP 실패 **0**, 네트워크 실패 **0**, 화면 이동 요청 취소 **0**.
- 실제 `pageerror` **0**, 콘솔 error **0**, warning **0**.
- 허용되지 않은 HTTP 요청/쓰기 요청 차단 발생 **0**. 쓰기 시도를 만들지 않았습니다.
- 정상 응답을 관찰한 리소스: JS **198**, CSS **198**, 이미지 **105**, 폰트 **1,183**. 페이지 재방문에 따른 중복을 포함한 횟수이며 자산 파일의 고유 개수가 아닙니다.
- 관리자 테이블의 의도된 401 응답은 독립된 음성 보안 검사입니다. 일반 페이지의 실패한 리소스 요청과 구분했습니다.
- 브라우저 요청은 실제 서버로 계속 전달하며 응답을 가짜 데이터로 교체하지 않았습니다. 실행은 1 worker로 순차 수행했으며 부하 테스트가 아닙니다.

## 4. 운영 데이터 보존과 대회 준비 상태

| 종목 | Revision 전→후 | 참가 반 | 경기 | 종료 경기 | 실제 날짜·시간 미입력 경기 | 예시 선수명 개수 | 공개 스냅샷 전후 동일 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 배구 | 17 → 17 | 6 | 9 | 0 | 9 | 48 | 예 |
| 피구 | 2 → 2 | 6 | 9 | 1 | 9 | 48 | 예 |

대회 기간에도 미설정 항목이 있습니다. 검증은 공개 대회 JSON의 SHA-256과 Revision을 비교했으며 선수명·관리자 이메일·키·응답 원문을 보고서에 넣지 않았습니다. 이 비교는 **전체 DB/Auth/비공개 이력의 백업 또는 전체 DB 무결성 검사**가 아닙니다.

### 대회 시작 전 반드시 확인할 항목

1. 두 종목의 대회 기간 및 **18경기 모두의 실제 연도·날짜·시간**을 관리자에게 확인해 입력합니다. 현재 월·일은 예시 일정일 수 있습니다.
2. 두 종목 각각 **48개 예시 선수명**을 실제 공개 대상 명단으로 교체하거나 명단 공개 범위를 확인합니다. 이번 작업에서는 명단을 변경하지 않았습니다.
3. 피구의 **기존 종료 1경기**가 실제 운영에 사용할 기록인지 확인합니다. 초기화나 삭제가 필요하면 백업과 별도 승인을 먼저 받습니다.
4. 실제 운영 관리자 계정의 로그인·로그아웃·두 종목 관리자 메뉴를 현장 기기에서 확인합니다. 이번 운영 자동화는 로그인/쓰기를 하지 않았습니다.
5. 복구 가능한 수동 SQL 백업과 복구 절차를 확인합니다. 공개 JSON 해시 확인만으로 복구 준비가 됐다고 판단하지 않습니다.

재현된 출시 차단 **코드 버그는 없음**으로 분류합니다. 위 준비가 끝나기 전에는 실제 대회 운영 준비 완료로 판단하지 않습니다.

## 7. 재실행·로그 보호

Node 22 환경에서 다음 명령을 사용합니다.

```powershell
npm run build
npm test
npm run test
npm run test:e2e
npm run test:simulation
npm run test:production
```

`test:production`은 실제 운영 사이트에 대한 읽기 검증입니다. 기존 `npm test`/`test:e2e`와 독립이며 로컬 개발 서버나 비밀번호가 필요하지 않습니다. 운영 테스트에는 .env 읽기, 로그인, storageState, trace, screenshot, video를 사용하지 않습니다. 공개 키는 사이트의 공개 요청에서 메모리로만 확인합니다. 브라우저에서는 지정된 공개 조회 RPC와 정적 리소스 요청만 허용하고, 명시적 API 도우미도 GET만 허용합니다. 요청 헤더·본문·공개 선수 명단·원문 콘솔 메시지를 첨부하지 않습니다. 실패 시 빈 문서로 이동한 뒤 요약 오류를 전달합니다.

주요 로컬 아티팩트(모두 `test-results/` 아래 Git 제외):

- `unit-results.json`: 실제 111개 개별 실행 결과.
- `local-browser-inventory.json`: 기존 50개 테스트 이름 목록. **목록 자체는 실행 결과가 아니며**, 별도로 수행한 전체 실행의 `50 passed` 결과와 대조했습니다.
- `simulation/results.json`: 최종 6개 로컬 추가 테스트 실행 결과.
- `production/results.json`: 최종 15개 운영 테스트 실행 결과와 개인정보를 제외한 감사 첨부.
- `production/summary.json`: 실제 리소스·오류·요청 수치 집계.
- `production/data-preservation.json`: 전후 해시·Revision·개수만 기록한 보존 확인. DB 백업 아님.

아래 상세 목록은 실제 JSON 실행 결과 및 기존 50개 전체 성공 결과를 기준으로 작성했습니다. 반복 실행으로 개수를 부풀리지 않았습니다.
